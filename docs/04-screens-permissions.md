작성: 2026-09-04 (KST)

## 0. 화면 설계 대원칙

**병동은 모바일 우선, 검사실은 PC 우선.**

같은 시스템이지만 쓰는 환경이 완전히 다르다.

| | 병동 간호사 | 검사실 간호사 |
|---|---|---|
| 주 사용 기기 | 폰 / 태블릿 (들고 다님) | 데스크톱 (고정 자리) |
| 사용 자세 | 한 손, 이동 중, 짧게 | 앉아서, 여러 건 동시에 |
| 필요한 것 | 빠른 요청 등록, 알림 확인 | 오늘 들어온 요청 전체 조망 |
| 화면 밀도 | 크게, 적게 | 촘촘하게, 많이 |

그래서 반응형이라고 해서 같은 화면을 늘렸다 줄이는 게 아니라,
**모바일 레이아웃과 데스크톱 레이아웃을 다르게 설계**한다.

### 3-3. 반드시 지킬 규칙 3가지

**(1) 간호기록은 절대 삭제되지 않는다**

의료 기록은 법적 증거물이다. 삭제 대신 정정 기록을 추가하는 방식으로 간다.
24시간 이내 본인 수정만 허용하고, 수정 시 원본을 이력으로 남긴다.

**(2) 파트 소속만으로 판단하지 않는다**

"MRI실 소속이니까 이 환자를 볼 수 있다"가 아니라
"**이 환자에 대해 우리 파트로 온 요청이 있으니까** 볼 수 있다"가 맞다.

```java
// 잘못된 검증
if (staff.getDepartment().getDeptType() == EXAM) { return true; }

// 올바른 검증
boolean hasRelatedRequest = transferRequestRepository
        .existsByEncounterIdAndToDepartmentIdAndStatusNotIn(
                encounterId, staff.getDepartment().getId(), TERMINAL_STATUSES);
```

요청이 완료되면 접근 권한도 같이 사라진다. 이게 의료 시스템의 최소권한 원칙이다.

**(3) 조회도 전부 감사 로그에 남긴다**

수정만 남기는 게 아니다. 환자 정보를 **열어본 것 자체**가 기록 대상이다.
`@Audited` 어노테이션을 컨트롤러 메서드에 붙이고 AOP 로 자동 적재한다.

```java
@Audited(action = "VIEW", targetType = "ENCOUNTER")
@GetMapping("/encounters/{id}")
public EncounterDetailResponse detail(@PathVariable Long id, ...) { ... }
```

### 실시간 갱신 처리 패턴

```typescript
// WebSocket 메시지를 받으면 직접 상태를 고치지 않는다.
// TanStack Query 의 캐시를 무효화해서 서버에서 다시 받아온다.
useEffect(() => {
  const subscription = stompClient.subscribe(
    `/topic/department/${myDeptId}`,
    (message) => {
      const event = JSON.parse(message.body);

      // 목록 다시 조회
      queryClient.invalidateQueries({ queryKey: ['transferRequests'] });

      // 해당 요청 상세를 보고 있다면 그것도 갱신
      queryClient.invalidateQueries({
        queryKey: ['transferRequest', event.requestId]
      });
    }
  );
  return () => subscription.unsubscribe();
}, [myDeptId]);
```

**WebSocket 메시지로 화면을 직접 그리지 않는다.** "다시 조회하라"는 신호로만 쓴다.
이렇게 하면 메시지를 놓쳐도, 순서가 뒤바뀌어도 화면은 항상 서버 상태와 일치한다.

## 5. 시연 시나리오 (최종 목표)

1. 노트북에 **MRI실 요청 큐(E-01)**, 폰에 **병동 환자 보드(W-01)** 를 띄운다
2. 폰에서 302호 김OO 카드 → **[+요청]** → 뇌 MRI, 응급 선택 → 등록
3. **노트북 큐에 즉시 빨간 행이 추가되고 알림음이 난다**
4. 노트북에서 요청 클릭 → 상세에 **"⚠ 좌측 고관절 인공관절 - MRI 금기 가능성"** 경고가 자동으로 떠 있다
5. 노트북에서 [접수] → 예정 15:30 입력 → **폰 카드 상태가 실시간으로 "접수됨 15:30" 으로 바뀐다**
6. 노트북 창을 하나 더 열어 같은 요청에 [준비완료]를 동시에 누른다 → **"다른 사용자가 먼저 처리했습니다"** 경고
7. 관리자 화면(A-01)에서 **"MRI실 평균 대기시간 31분"** 통계를 보여준다

**3분.** 이 시나리오가 끊김 없이 돌아가면 프로젝트는 성공이다.
6번(동시성 충돌 시연)이 다른 포트폴리오와 확실히 갈리는 지점이다.

## 6. 작업 순서 제안

| 순서 | 작업 | 산출물 |
|---|---|---|
| 1 | 프로젝트 생성 + Flyway 스키마 | 실행되는 빈 서버 |
| 2 | 인증/권한 + 마스터 CRUD | 로그인 되는 서버 |
| 3 | 이송 요청 도메인 (상태 전이 + 테스트) | 단위 테스트 전부 통과 |
| 4 | 이송 API + 화면 W-01~W-05, E-01~E-02 | 요청이 오가는 화면 |
| 5 | WebSocket 실시간 | 시연 시나리오 1~5번 완성 |
| 6 | 동시성 처리 + 통계 화면 | 시연 시나리오 6~7번 완성 |
| 7 | 간호기록 + 감사로그 | 완성도 보강 |

3번까지는 화면 없이도 만들 수 있다. **테스트 코드로 검증하면서 진행**하는 게 가장 빠르다.
