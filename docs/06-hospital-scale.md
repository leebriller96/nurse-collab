## 1. 무엇을 바꾸는가

두 가지다. 서로 독립이지만 같은 방향을 본다.

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 업무 | 이송 요청 하나 | 부서 간 업무 요청 일반(이송·검체·약제·의공) |
| 데이터 | 한 DB 에 전부 | 환자 관련은 원내, 업무 흐름은 클라우드 |

### 왜 일반화인가

`transfer_request` 가 하는 일을 떼어놓고 보면 이송에만 해당하는 것이 없다.
A부서가 B부서에 걸고, 상태가 전이되고, 이력이 남고, 실시간으로 퍼지고, 대기시간이 집계된다.
검체 검사도, 약제 조제도, 장비 수리도 정확히 같은 모양이다.

그래서 **부서를 늘리는 대신 추상을 한 단계 올린다.**
부서마다 도메인을 새로 만들면 얕은 CRUD 가 부서 수만큼 늘어난다.
하나로 올리면 부서가 늘어도 도메인은 하나고, 상태 규칙은 여전히 한 곳에만 있다.

### 왜 분리인가

진료기록은 밖에 두기 어렵고 협업 도구는 밖에 있어야 폰에서 열린다.
보통 "전부 원내에 두고 VPN" 으로 도망가는데, 그러면 폰에서 못 쓴다.
**데이터를 통째로 옮기지 말고 등급으로 갈라야 한다.**

## 2. 원칙

### 하기로 한 것

1. **환자를 사람으로 되돌리는 열쇠는 원내에만 둔다.** 클라우드 DB 를 통째로 가져가도
   누구인지 알 수 없어야 한다.
2. **합치는 곳은 서버가 아니라 브라우저다.** 서버에서 합치면 클라우드가 이름을
   지나가며 보게 되고, 나눈 의미가 절반 날아간다.
3. **원내에 못 닿으면 감추지 말고 그렇다고 말한다.** 오프라인에서 낡은 값을 내놓지 않기로 한 것과 같다.
   모르는 것보다 틀리게 아는 것이 나쁘다.
4. **상태 전이 규칙은 여전히 한 곳에만 있다.** 종류가 늘어도 이 규칙은 흔들리지 않는다.

### 하지 않기로 한 것

| 항목 | 안 하는 이유 |
|---|---|
| EMR 대체 (처방, 수가, 청구) | 이 프로젝트는 EMR 옆에 붙는 협업 레이어다. 포지셔닝을 바꾸면 전부 얕아진다 |
| 부서마다 별도 도메인 | 같은 모양을 여러 벌 만드는 것이다. `WorkOrder` 하나로 올린다 |
| 원내 DB 를 클라우드로 복제 | 복제하는 순간 분리한 의미가 사라진다. 백업도 원내에서 끝난다 |
| 클라우드가 원내를 호출 | 방향이 반대다. 원내는 받기만 하고 먼저 나가지 않는다 |

## 3. 데이터 등급

### 판정 기준

> **사람을 가리키거나 건강을 말하면 원내.**
> 업무가 언제 어디서 누구(직원)에 의해 어떻게 흘렀는지는 클라우드.

| 등급 | 내용 | 사는 곳 |
|---|---|---|
| 식별정보 | 이름, 생년월일, 등록번호, 연락처, 보호자 연락처 | **원내** |
| 진료정보 | 진단명, 간호기록, 활력징후, 주의사항 내용, 거동 가능 여부 | **원내** |
| 업무정보 | 요청 상태, 시각, 부서, 담당 직원, 업무 항목, 우선순위 | 클라우드 |
| 집계 | 평균 대기시간, 부서별 처리량 | 클라우드 |

직원 정보(`staff`)는 클라우드에 둔다. 개인정보이긴 하나 환자의 것이 아니고,
로그인과 권한 판정이 클라우드에서 일어나야 하기 때문이다.

### 회색지대 두 개와 그 판정

**(1) 거동 가능 여부(`is_mobile`)** — 이송 준비물(휠체어/침대)을 정하는 값이라
업무정보로 보고 싶어진다. 그러나 이것은 그 사람의 건강 상태다. **원내로 둔다.**
검사실 큐의 "침대 이송" 표시는 원내망에서만 뜬다. 기준을 한 번 느슨하게 하면
다음 회색지대는 더 쉽게 넘어간다.

**(2) 업무 항목(`뇌 MRI`)이 클라우드에 남는 것** — `subject_ref` 와 붙으면
"이 사람이 뇌 MRI 를 받았다" 가 되어 진료정보에 가깝다.
그런데 이것 없이는 검사실이 무엇을 준비할지 모르므로 업무 자체가 성립하지 않는다.
**클라우드에 두되, 재식별 열쇠가 원내에만 있으므로 가명정보로 취급한다.**
이것이 이 설계에서 가장 양보한 지점이고, 그래서 여기 적어 둔다.

## 4. 배치

```
        폰 / 노트북 (원내망 안)
                │
        ┌───────┴────────┐
        │                │
   공개 도메인        사설망 주소
   (클라우드)         (원내 게이트웨이)
        │                │
   업무 흐름          이름·기록·주의사항
   subject_ref 로만    subject_ref → 사람
   환자를 가리킴       대응표가 여기에만 있다
```

**클라우드는 환자 이름을 한 번도 본 적이 없다.**

원내망 밖에서 열면 클라우드만 붙고, 화면은 업무 흐름을 그대로 보여주되
환자 자리에는 `원내망에서만 조회됩니다` 가 뜬다. 기능이 고장 난 것이 아니라
설계대로 줄어든 것이다.

### 연결 규격

| | 클라우드 | 원내 게이트웨이 |
|---|---|---|
| 주소 | 공개 도메인 (HTTPS) | 사설망 주소 |
| 경로 | `/api`, `/ws` | `/phi` |
| 인증 | 토큰 발급 + 검증 | 검증만 |
| 저장 | 업무 DB | PHI DB (별도 PostgreSQL) |

## 5. 인증 — HS256 을 RS256 으로 바꾼다

지금은 대칭키다. 원내가 토큰을 **검증**하려면 클라우드와 **같은 서명 키**를 나눠 가져야 하고,
그 순간 원내가 클라우드 토큰을 위조할 수 있다. 원내 키가 새면 클라우드도 같이 뚫린다.

**클라우드가 개인키로 서명하고, 원내는 공개키로 검증만 한다.**
원내는 토큰을 만들 수 없다.

### 한계를 숨기지 않는다

이렇게 해도 **클라우드가 뚫리면 간호사 토큰을 새로 발급해 원내에 물어볼 수 있다.**
클라우드가 인증 서버인 이상 이 구멍은 구조적으로 남는다. 완벽한 차단이 아니다.
그래서 원내 게이트웨이에 두 가지를 둔다.

1. **조회량 제한** — 한 직원이 짧은 시간에 많은 환자를 여는 것을 막는다.
   정상 근무에서는 담당 환자 수를 넘지 않는다. 대량 유출은 여기서 걸린다.
2. **원내 자체 감사 로그(`phi_access_log`)** — 클라우드의 `audit_log` 와 별개다.
   클라우드가 건드릴 수 없는 곳에 흔적이 남아야, 뚫렸을 때 무엇이 나갔는지 알 수 있다.

막는 것이 아니라 **좁히고 남긴다.** 이것이 정직한 선이다.

## 6. WorkOrder 일반화

### 종류와 상태

상태는 하나의 `OrderStatus` 로 모으되, **어떤 상태를 쓰는지와 전이 규칙은 종류가 갖는다.**
규칙표가 `TransferStatus.RULES` 에서 `OrderType` 별 규칙표로 옮겨갈 뿐,
"규칙은 한 곳에만 있다" 는 원칙은 그대로다.

| 종류 | 요청 → 수행 | 환자 | 흐름 |
|---|---|---|---|
| `TRANSFER` 이송 | 병동 → 검사실 | 있음 | 요청 → 접수 → 준비완료 → 이송중 → 검사중 → 복귀중 → 완료 |
| `SPECIMEN` 검체 | 병동 → 진단검사의학과 | 있음 | 요청 → 접수 → 채취완료 → 검사중 → 결과등록 → 완료 |
| `PHARMACY` 약제 | 병동 → 약제부 | 있음 | 요청 → 접수 → 조제완료 → 불출 → 완료 |
| `EQUIPMENT` 의공 | 병동 → 의공학팀 | **없음** | 요청 → 접수 → 수리중 → (부품대기) → 완료 |

`ON_HOLD` 와 `CANCELLED` 는 모든 종류가 공유한다.

### `EQUIPMENT` 를 넣는 이유

이송·검체·약제만 넣으면 전부 "환자가 있고 병동이 건다" 라서 일반화가 되었는지 알 수 없다.
장비 수리는 **환자가 없다.** 그래서 `work_order.subject_ref` 가 NULL 을 허용해야 하고,
환자 접근 판정이 이 요청에는 아예 걸리지 않아야 한다.
이 한 종류가 일반화가 진짜인지 아닌지를 가른다.

### 환자 접근 판정은 그대로다

지금 규칙은 "우리 부서로 걸린 진행중 요청이 있으면 볼 수 있다" 다.
`transfer_request` 가 `work_order` 로 바뀌어도 문장이 같다.
다만 판정이 **원내 게이트웨이에서 일어난다.** 게이트웨이는 클라우드에
"이 직원이 이 `subject_ref` 에 관여하고 있는가" 를 물어 답을 받는다.
판정 로직을 원내에 다시 구현하지 않는다. 두 곳에 두면 한쪽만 고쳐지는 날이 온다.

### 이름 바꾸기

| 지금 | 바꾼 뒤 | 이유 |
|---|---|---|
| `transfer_request` | `work_order` | 이송만이 아니다 |
| `transfer_event` | `work_order_event` | |
| `exam_type` | `service_item` | 검사만이 아니다. 부서가 제공하는 업무 항목 |
| `TransferStatus` | `OrderStatus` | |
| `TR20260904-0001` | `TR-` / `SP-` / `PH-` / `EQ-` 접두사 | 번호만 보고 종류를 안다 |

## 8. 단계

**순서를 이렇게 두는 이유:** 1단계는 DB 를 하나로 유지한 채 이름과 구조만 바꾼다.
끝나도 배포 모양이 그대로라 언제든 멈출 수 있다.
2단계부터 되돌리기 어려워지므로, 1단계가 전부 초록이 된 뒤에 들어간다.

### 1단계 — WorkOrder 일반화 (DB 한 개 유지)
- `V8` 이름 변경 + `order_type`, `subject_ref` 컬럼 추가
- `OrderType` 별 규칙표, 기존 이송 테스트 전부 통과 유지
- 검체·약제·의공 종류 추가, 부서 3개 추가
- 화면: 병동 요청 등록에 종류 선택, 수행 부서 큐를 종류별로

### 2단계 — 데이터 등급 분리
- PHI 를 원내 스키마로 이전, `subject_ref` 발급
- 원내 게이트웨이 모듈(`onprem/`), `phi_access_log`, 조회량 제한
- RS256 전환
- 프론트 이중 클라이언트, `원내망에서만 조회됩니다` 표시

### 3단계 — 배포와 시연
- compose 두 덩어리, 원내는 사설망에만 노출
- 브라우저 검사: 원내망을 끊었을 때 업무는 돌고 이름만 사라지는지

## 9. 아직 답하지 못한 것

정직하게 남겨 둔다. 2단계 들어가기 전에 결정해야 한다.

1. **`request_message` 의 대화 내용.** "환자분 열이 38.5도라 검사 미뤄주세요" 같은 말이
   섞일 수 있다. 내용을 원내로 보내면 원내망 밖에서 대화가 통째로 안 보인다.
   현재 기울어진 쪽: **원내로 보낸다.** 업무는 상태 전이로 돌아가고 대화는 부가 수단이다.
2. **통계.** 대기시간 집계는 클라우드만으로 되지만, 병동별로 쪼개는 순간
   `care_episode` 가 필요하다. 지금 배치로는 된다. 진단명별 집계를 원하면 못 한다.
3. **원내 게이트웨이가 죽었을 때 쓰기 동작.** 주의사항 남기기는 원내로 가는 쓰기다.
   못 닿으면 큐에 쌓아 두고 나중에 보낼 것인가? **아니다.** 간호 기록을 나중에
   보내는 것은 시각이 어긋난 기록을 만든다. 실패로 알리고 다시 시도하게 한다.

## 10. 되돌리는 법

작업은 `feature/hospital-scale` 에서 한다.
`master` 는 지금 상태(이송 전용, 단일 배포)로 언제든 시연 가능하게 남긴다.
1단계까지는 `master` 로 되돌려도 잃는 것이 없고,
2단계부터는 데이터 이전이 섞이므로 되돌릴 때 원내 DB 를 다시 합쳐야 한다.
